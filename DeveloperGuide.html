Setting up, getting started

Refer to the guide Setting up and getting started.

TAB supports JavaFX 17.0.7, supplied by Gradle and bundled in the release JAR. Use an x64 JDK 25 without bundled JavaFX to build and test this baseline. CI tests it on Linux, macOS, and Windows. TAB also supports the course's Mac setup, Zulu JDK+FX 25.0.3, which uses the JDK's JavaFX 25 instead. A separate macOS CI job tests that setup on Apple Silicon. The bundled JavaFX native libraries target x64. Apple Silicon Macs therefore need an x64 JDK running under Rosetta when using plain JDK + JavaFX 17. An ARM64 plain JDK cannot load these libraries. The course's native ARM64 JDK+FX setup supplies its own JavaFX libraries and does not need Rosetta.

Design

Architecture

The Architecture Diagram given above explains the high-level design of TAB.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of TAB's launch and shut down.

  • At TAB's launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of TAB's work is done by the following four components:

  • UI: The UI of TAB.
  • Logic: The command executor.
  • Model: Holds the data of TAB in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, StudentListPanel, SummaryPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes commands entered by the User using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Student objects from the model.

The student card's secondary row reserves one pixel at its right edge because JavaFX 17's HBox can leave one pixel undistributed when shrinking children. This keeps the email inside the details area at narrow widths, including when platform fonts produce different preferred label widths.

The student card's TagRow retains every tag name, but creates at most three tag labels. Layout uses the full name count to size the overflow chip and list all hidden tags in its tooltip, even when fewer labels are created.

Student-card email labels use UiText.showToFit to retain their full text and show a tooltip only while the available width cuts the address. Width listeners remove the tooltip when widening the card makes it unnecessary.

HelpWindow re-fits its scene after the first rendering pulse, allowing for native frame sizes, then uses sizeToScene() without fixed FXML scene dimensions. This lets JavaFX include native decoration sizes correctly. Its copy button keeps the same border insets when focused, so the focus indicator does not increase the content's preferred size. The regression test waits for rendering and native resize events, then measures the scene rather than its surrounding frame.

Fitting names and tags on a card

CardHeadline reserves a readable start of the name before allocating room to tags. When that leaves no room for a tag chip, TagRow uses the shorter N tags total instead of N more…, preserving a complete count beside the name. Its tooltip still lists every hidden tag.

Colouring the command line

CommandTextField converts tab and line separators to spaces in text replacement before JavaFX filters control characters. It preserves pasted word boundaries while keeping the command on one line, including when a paste replaces selected text. CRLF is treated as one separator.

A TextField cannot colour its own content, so CommandBox keeps the field for input and draws a coloured copy of the command behind it, with the field's own text transparent. The field still takes every keystroke and still decides which character a click lands on, which keeps editing exactly as it was.

CommandHighlighter decides the colours. It returns spans covering every character of the command. It walks the command itself, rather than calling CommandTokenizer, because it has to keep the text exactly as typed, quotes and all, where the tokenizer removes them and may refuse an unclosed quote that is merely half-typed. It asks the tokenizer the questions the two must agree on — CommandTokenizer#isEscapable, and StringUtil#isWhitespace for where a token ends — and CommandHighlighterTest runs both over a list of awkward commands and compares how many tokens each found. That catches one of them splitting a command into a different number of pieces; it does not compare where each piece begins and ends, so a boundary that moves without changing the count slips through. It never rejects anything: a command is coloured while it is still half-typed.

Three things then have to agree with the field, because the User reads our copy but interacts with the field:

  • the scroll offset. The copy is drawn wherever the field is drawing its own text, read from the field's text node rather than worked out again here. A field scrolls by rules that differ between typing, deleting, cutting and undoing, and every attempt to reproduce them was right for some of those and wrong for others; a copy even a pixel out of step shows one character where the field hit-tests another, and clicks land in the wrong place. Reading that node once is not enough, because the field's skin re-scrolls it after a delete, a replace or a change of width, which is after the caret and the text the colouring was told about have both settled. The copy therefore follows the node's own position. The node is the one the field is drawing in, since an empty line shows the prompt in a node of the same kind which the field hides rather than throws away, and a command reading as the prompt would otherwise be taken for the hidden one.
  • the caret. The field's caret is drawn in its text colour, which is transparent, so the line carries one of its own, sized from a run of the text so it sits where the text does.
  • the selection. The field draws its highlight at its own offset, which broke into fragments behind the copy, so it is turned off in the stylesheet and drawn here instead.

CommandBoxTest checks the contrast of the selection band against the line, and of every colour the line uses against that band, including the one a refused command is written in, so that selecting a command cannot hide half of it. The bar it holds them to is 3:1 rather than the 4.5:1 WCAG asks of text this size: on a window this dark, a band light enough to be seen against the line (2.2:1) lightens the background enough that 4.5:1 would need every token colour moved towards white, which is not the palette the mockup sets. The trade-off is deliberate and worth revisiting if the palette changes.

Recalling session commands

CommandBox records each submitted line in CommandHistory before execution, so rejected input can be recalled too. The helper stores submissions separately from the draft captured when Up first leaves the newest position. Down past the newest submission restores that draft. Up skips the newest submission when it already matches the text in the box and an earlier entry exists. Blank submissions and consecutive identical submissions are skipped; editing a recalled entry does not alter stored text.

The command box consumes unmodified Up/Down key presses before the text field handles them. Recalled text uses the existing text listener for colouring, and the caret moves to its end. This UI state is session-only and never enters the student model or persisted data.

Summarising the list

SummaryPanel shows the flagged count, a count per tag and the total, beside the list. It counts Logic#getFilteredStudentList(), which is the only list Logic exposes, so it summarises what the list is showing rather than the whole student book: after find Alex it counts the matches. That is the reading the User Guide documents, and it keeps the panel answering the same question as the list it sits beside. Summarising the whole book instead would need Logic to expose it.

The list is an ObservableList, so a listener keeps the counts current without the panel being told when a command changes anything. The counting itself is static and takes a plain List<Student>, so it is tested without a toolkit; only the rendering needs one.

Tags counted the same are listed alphabetically ignoring case, because a reader does not read Zoo as coming before apple.

Model component

API : Model.java

The Model component,

  • stores the student book's data i.e., all Student objects (which are contained in a UniqueStudentList object).
  • stores the Student objects selected by the current filter, such as search results, in a separate filtered list. It exposes this list as an unmodifiable ObservableList<Student> that the UI can observe and bind to, so the UI updates when the list changes.
  • stores a UserPrefs object that represents the User’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Note: The alternative, arguably more object-oriented, design below keeps a unique list of tags in StudentBook, and each Student references tags from that list. This lets StudentBook maintain one Tag object per unique tag instead of each Student holding its own Tag objects.

Storage component

API : Storage.java

The Storage component,

  • can save both the student book's data and the User's preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonStudentBookStorage and JsonUserPrefsStorage (one class per data file).
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

Implementation

This section describes some noteworthy details on how certain features are implemented.

How commands read their arguments

add and edit mark their fields with options, add NAME -p PHONE [-e EMAIL] [--id NUS_STUDENT_ID] [-t TAG]... [--follow-up] and edit INDEX [-n NAME] [-p PHONE] [-e EMAIL] [--id NUS_STUDENT_ID] [-t TAG]... [--follow-up | --no-follow-up], where AB3 marked them with prefixes such as p/. The value options have descriptive long aliases: --name, --phone, --email, and --tag correspond to -n, -p, -e, and -t respectively. add takes its name in the preamble, so --name applies only to edit.

A prefix has to be a sequence a value never contains, and no such sequence exists for a name. s/o, d/o, a/l and a/p are ordinary parts of Singaporean and Malaysian names, and a/l was in fact unreadable for as long as an address field was marked a/. Widening the prefixes would only move the collision somewhere else. Options move the problem out of the value entirely: an option is a whole token, so a name is read as a name however it is spelled.

Parsing runs in two passes, the way a shell does it.

CommandTokenizer splits the arguments on whitespace and lets double quotes group a value containing whitespace. A token records whether a quote took part in it, because that is the only thing separating the value -Ahmad from the option -e. A backslash escapes a quote or another backslash, so a value may hold either; a backslash before anything else stays in the value, so nothing the User typed disappears without being asked for.

An option appearing where a value is expected is read as the option before it having been left empty, rather than as a value. add John -p 123 -t -e reports that -t needs a value instead of storing -e as a tag. A value that really does open with a hyphen is given in quotes.

FlagTokenizer reads the tokens. Those before the first option are the preamble, joined with single ASCII spaces, which each command reads as whatever it takes in that position: the name for add, so a name of several words needs no quotes unless it would otherwise be misread, and the index for edit. Each command names its own, in AddCommand.FIELD_NAME and EditCommand.FIELD_INDEX, rather than the shared CliFlags doing it for them. Each short and long marker resolves to the same Flag, so mixed aliases for a single-valued field are duplicates rather than independent fields. Value-taking options take the token after them, and -t or --tag repeats. The presence-only --follow-up option (alias -f) and edit-only --no-follow-up option (alias -nf) instead record an empty value and consume no following token. This lets FlagArgumentMap distinguish an absent option from a present marker without a separate representation. An unknown option, a value-taking option left without a value, and a token belonging to no option are each reported for what they are, rather than as one generic complaint.

Flag also lets a value-taking option carry aliases. NUS Student ID uses --id as its canonical option and the unused -i as its typing-friendly alias. Both spellings map to the same FLAG_NUS_STUDENT_ID, so giving both is rejected as a repeated single-valued field rather than letting one silently override the other. Usage labels and error messages use the canonical --id NUS_STUDENT_ID spelling.

The shape of the command is settled before any field is read. An unclosed quote, an unknown option, or a single-valued option given twice, including once under each alias, all leave it unclear which field a value belongs to, so each is refused on its own instead of being collected with the field errors.

edit clears a field with an explicitly empty value rather than with a bare option. -e "" removes the email, --id "" removes the NUS Student ID, and -t "" removes every tag. Email and NUS Student ID values are trimmed before this check, so quoted whitespace clears either optional field too. A bare option cannot mean "clear" here, because a bare option is what reports the mistake in edit 1 -t -e a@b.com: the -e is read as the value -t was left without, rather than being stored as a tag. An empty quoted value also separates a value left empty by accident from one cleared on purpose. CommandTokenizer produces an empty token for "" and leaves the decision to the field parser, so no tokenizer change was needed.

edit sets follow-up with --follow-up (alias -f) and clears it with --no-follow-up (alias -nf). The parser rejects contradictory options before describing any edit, so neither the model nor the saved book changes on that error. The -nf alias makes clearing quick to type without making opposite actions differ only in case, as -f and -F would. Both clear spellings map to the same option, so mixing them is also detected as a duplicate.

Commands with no arguments

StudentBookParser rejects non-whitespace input after clear, list, help, and exit before returning a command. Its existing Unicode whitespace rule accepts pasted whitespace as well as spaces and tabs. The feedback names the command and unexpected input, with long input shortened to keep the reason visible. Quotes do not make an argument absent: clear "" is refused too. A parse failure reaches neither command execution nor LogicManager's storage write, so it preserves both the displayed list and the JSON file.

Suggesting a command word

A command word TAB does not dispatch on is answered with the word the User typed and the command words it is a likely attempt at. CommandWords works out which those are in two steps: what the typed word opens, and, failing that, what it is near.

A word that opens a command word is read as that command word being typed. del stands for delete, although help is the nearer of the two by edits alone, at two against three. A part-typed word is right as far as it goes, which says more about what was meant than the distance to some other word does. Only a word that opens nothing is measured for edits at all.

The measure is StringUtil.editDistance: how many insertions, deletions, substitutions and swaps of neighbouring characters turn one word into the other. A swap counts as one edit because a fast typist makes them as readily as the other three, and lsit would otherwise sit two edits from list, as far away as a wilder guess.

Two edits is the budget for every command word, whatever its length. That is what the user story asks for, and it is what reaches the words a teaching assistant types: ls opens nothing and is two insertions short of list, and dlte is two deletions from delete.

Two edits also reach past the first letter of a short command word, which is how dlt came to be answered with edit. A word measured for edits therefore has to open with the character the command word opens with, unless the single edit between the two is that character. The first letter is the one a typist is least likely to get wrong, so a word two edits out that disagrees on it as well has little to do with the command it happens to sit near; where one edit is the whole difference, that edit may fall on the first letter and the rest of the word already agrees, which keeps felete, edlete and elete reading as delete.

Every command word equally likely is named. eit is a letter short of both edit and exit, and answering with edit alone would read as knowledge TAB does not have, with the other ruled out. Choosing between equally likely words dresses a guess up as help, while naming them all says exactly what is known. They are named in the alphabetical order of COMMAND_WORDS, so one typo always draws one reply.

Past three equally likely words the reply falls back to the pointer to help, because a list that long says only that TAB cannot tell. No typed word reaches that with the command words TAB has: edit and exit are the only two sharing a first letter, so at most two are ever named at once, and the limit is there for the command words it may gain.

The comparison folds case, so LIST is read as an attempt at list, while the message quotes the word as it was typed, because a User who typed capitals needs to see them to recognise what they did. The quoted word is shortened the way a rejected field value is, so that a pasted line cannot push the rest of the message out of sight. Lengths are compared before any distance is, which also settles such a line against every command word without measuring it.

A suggestion is never run. Dispatching delete for dlte would act on a word the User did not type, and a wrong guess there costs a student record, where a wrong suggestion costs a line of text. StudentBookParser raises the same ParseException as it does for any unknown word, which leaves the model, the saved file and the typed text in the command box as they were.

The parser dispatches with a switch rather than from CommandWords.COMMAND_WORDS, so the two can disagree: a word missing from the list would work when typed while being suggested to nobody. CommandWordsTest resolves the command words out of the parser's own cases and compares them against the list rather than leaving that to be noticed.

Follow-up flag

Flag extends Tag and uses its validation, normalization, and display behavior. Its fixed name is Needs follow-up. A general tag with those words remains a distinct value: tag equality requires the same concrete class as well as the same normalized name. Student holds an optional Flag and exposes it through getFlag(); isFlagged() preserves the existing boolean interface for commands and the UI. Full equality and hashing include the flag, but isSameStudent does not: changing whether a student needs a reply does not change their identity. The four-argument constructor defaults to no flag so existing callers remain source-compatible.

Search combines ordinary tags with the optional flag and matches their inherited tagName values. The student card and command feedback display the same value, while the card keeps the flag in its separate follow-up row.

The add parser maps the presence of --follow-up, or its -f alias, to true. For edit, the EditStudentDescriptor stores a nullable Boolean isFlagged: null preserves the existing state, true sets follow-up, and false clears it. getFlagged() exposes this as an Optional<Boolean>. EditCommand uses the requested value when present, otherwise the selected student's existing state. This makes either request safe to repeat while preserving follow-up during unrelated edits. Descriptor copies and equality retain all three states.

JsonAdaptedStudent uses a nullable Boolean flag at the storage boundary. Only Boolean.TRUE creates a Flag in the model; a missing key, JSON null, and false all map to no flag. When saving, a present flag is written as "flag": true, while an absent flag is represented as null and omitted by Jackson's NON_NULL policy. Files created before the field existed therefore load without migration or gratuitous rewrites.

StudentCard shows a Needs follow-up label for true. For false it makes the label both invisible and unmanaged, so the card keeps no blank placeholder row. Successful add, edit and delete feedback formats student records consistently with the student card: optional fields (email, tags, follow-up status) appear only when present, with tags ordered alphabetically ignoring case, avoiding placeholder labels or empty tag markers.

Field values

Name, Tag and Phone each store the form returned by StringUtil.normalizeFieldValue: without zero-width characters, with each run of whitespace reduced to one ASCII space and leading and trailing whitespace removed, and with the result composed to Unicode NFC. Composing happens last, because a zero-width character between a base letter and its combining mark blocks the two from composing.

They normalize for different reasons, and the rule each one enforces differs.

Field Why it is normalized What it must hold
Name it is the identity field used to compare students, so visually identical names should have the same stored form at least one letter or number
Tag it is a key in the set of a student's tags, so two that look alike must not both be stored at least one letter or number
Phone it is displayed beside the others and gains nothing from being stored differently at least 3 digits

The NUS Student ID may be absent. NusStudentId accepts between 1 and 32 ASCII letters and digits. Input letters are case-insensitive and the value is stored in uppercase, so e0123456 and E0123456 are the same value. This accommodates variations in the identifiers issued to different groups of students while preventing an accidentally pasted value from hiding the other details on a student's card. Student holds a nullable NusStudentId and exposes it as Optional<NusStudentId>, matching the existing optional-email boundary without inventing a sentinel value. NusStudentId.getFailureReason performs the single validation scan, and isValidNusStudentId delegates to it. This keeps the accepted format and the specific user-facing error synchronized without maintaining a separate regex.

The add and edit parsers read either --id or -i through the same flag and validate with ParserUtil.parseNusStudentId. Add leaves the field absent when no option is given. For edit, EditStudentDescriptor.OptionalFieldEdit encapsulates the value and edit intent as one three-state concept: an absent option preserves the old value, a present non-empty option replaces it, and --id "" clears it. The edit parser trims the supplied value before this check, so a quoted value containing only spaces also clears the field. Descriptor copies and equality operate on this encapsulated state, rather than repeating knowledge of its internal representation.

JsonAdaptedStudent represents the storage property as a nullable string. Jackson omits it on save when no ID is present; both a missing nusStudentId key and JSON null load as absent, preserving files written before the field existed. A malformed non-null value rejects the data file instead of being silently dropped. The student card and command feedback show a present ID and omit the label entirely when absent.

NUS Student ID is searchable but is not an identity key. Student identity remains the normalized name, so two different names may carry the same NUS Student ID, just as they may carry the same phone or email. This avoids rejecting legitimate data or claiming certainty when a reused detail might be a correction or a data-entry mistake. Adding or editing a record to a name already in the book is still rejected. A future duplicate-warning workflow can surface shared contact details without changing this model contract.

The email may be absent. A student is recorded before an email address is known rather than one being invented. Student retains its nullable email constructor contract and exposes the value as Optional<Email> so callers handle absence explicitly. JsonAdaptedStudent writes the email as a string when present; the optional wrapper is not written to JSON.

The data file simply carries no email key. One that holds a malformed address is still refused, rather than the address being quietly dropped.

edit INDEX -e "" clears an email without removing the student or changing other fields. EditStudentDescriptor stores an Optional<Email> and records isEmailEdited separately: false leaves the existing value alone, true with an empty optional clears it, and true with an address replaces it. setEmail requires an address and clearEmail explicitly requests removal. Both mark the email as edited, so callers cannot toggle the intent independently of the replacement value. Copies use those same methods to preserve all three states. The descriptor is not persisted, so its optional field does not affect JSON.

The parser leaves the email untouched when -e is absent, calls clearEmail for a token that is empty after trimming, and sets a replacement only after validation succeeds. A rejected value is recorded as a parse problem without assigning a null email or requesting a clear. A bare option is still an error. Clearing counts as an edit even when the email is already absent. EditCommand keeps the value optional until the existing Student constructor boundary. The saved record omits the email key and reloads through the existing optional-email storage contract.

Email.MAX_LENGTH caps at 254 characters the address a command may enter. ParserUtil.parseEmail checks Email.isWithinLengthLimit before Email.isValidEmail, and getFailureReason carries the same guard because it matches the local part on its own.

The limit is not there to simplify validation, which the guidance on arbitrary limits rules out. VALIDATION_REGEX nests one quantifier inside another, ([+_.-][^\W_]+)*, and Java matches a repeated group by recursion, one frame per repetition, so an address with enough .-separated groups exhausts the stack. StackOverflowError is an Error that no parser catches, and CommandBox catches only CommandException and ParseException, so the User saw no feedback at all. 254 is the limit RFC 5321 section 4.5.3.1 puts on a forward path, so the bound comes from the domain rather than from the parser. It is not the product's only bound: a NusStudentId holds at most 32 characters, while Name, Phone and Tag are checked for the content they hold rather than for their length, and take a value of any size. What is particular to this bound is its purpose, which is to keep VALIDATION_REGEX from walking an address long enough to exhaust the stack, and 254 is the longest measured to be safe on every stack size tried: on a 256 KB stack even a 513-character address overflows.

isValidEmail deliberately keeps no length limit, so each input boundary can report length and format failures separately. Both ParserUtil and JsonAdaptedStudent check Email.MAX_LENGTH before calling the matcher. A saved address of up to 254 characters therefore loads, while a longer one raises IllegalValueException with its actual and allowed lengths before its shape can exhaust the stack. The storage tests cover both sides of that boundary.

Messages.getErrorMessageForInvalidValue shortens a rejected value past MAX_QUOTED_VALUE_LENGTH characters, so that a very long value cannot push the reason out of view. It counts characters through StringUtil.firstCharacters, as a reader counts them, so it separates neither an emoji nor a letter from the accent that belongs to it; a student card cuts a name or a tag with the same helper. Command parsing and storage share that message, so both paths report the same invalid value consistently.

Phone is not an identity field and not a key: two students may hold the same number, and isSameStudent does not read it. It is normalized only so that a number typed with unusual whitespace is stored consistently.

FindCommandParser reads search arguments using CommandTokenizer, allowing keywords to be enclosed in double quotes to match phrases containing spaces (such as "Lab 3"). Unterminated quotes report CommandTokenizer.MESSAGE_UNCLOSED_QUOTE, while empty or whitespace-only quoted terms are rejected with MESSAGE_EMPTY_KEYWORD. Search terms are normalized with StringUtil.normalizeFieldValue, collapsing internal whitespace runs and applying Unicode NFC normalization. It creates a DetailsContainsKeywordsPredicate, which checks each keyword or phrase against the student's name, NUS Student ID, phone, email, ordinary tags, and optional follow-up flag. Matching is case-insensitive and partial; any keyword can match.

FindCommand and ListCommand report the count of displayed students in their execution feedback. FindCommand counts only the matching students (Messages.getStudentsFoundOverview), distinguishing zero (Found 0 students.), singular (Found 1 student.), and plural (Found <n> students.) results. ListCommand reports the number of students displayed after resetting the filter (Listed 0 students., Listed 1 student., or Listed <n> students.).

Nothing else is rejected in any of the three. A phone number may hold +, whitespace, brackets and an extension; a tag may hold whitespace, hyphens and any script. None of those characters can hinder TAB, because none of these fields is parsed, dialled, or used to build a file path.

Handling an unreadable data file

Startup distinguishes a missing student-book file from an unreadable one. A missing data/tab.json is a first launch and receives the sample student book. An existing file is first parsed as JSON and then every student record and field is converted to its model type. Both stages finish before the normal UI can accept a command.

JsonUtil turns malformed JSON or an incompatible JSON shape into a DataLoadingException that retains the parser's line and column. During model conversion, JsonAdaptedStudent identifies the invalid field and JsonSerializableStudentBook adds the one-based record number and its name when available. JsonStudentBookStorage carries that explanation through the same DataLoadingException boundary.

MainApp records a student-book loading error and creates an empty model only as an internal placeholder so that application shutdown remains safe. It gives the error to UiManager. Before constructing MainWindow, UiManager checks for that error. If one is present, it shows an error dialog containing the data-file path, the specific reason, and recovery guidance. Closing the dialog closes TAB because the normal window was never opened. No command, including exit, can therefore save the placeholder over the unreadable file.

Failing closed was chosen over displaying a partial or read-only student book. It keeps recovery small and unambiguous: the User repairs or replaces the file and restarts TAB. Loading readable records separately and reloading without a restart remain separate future features.

Student names

A name is displayed, searched as text, and used as a student's identity field. Name therefore stores a normalized field value rather than the raw input, so that two names which look identical cannot be searched differently or admitted as two students.

Normalizing. On construction a name is

  • composed to Unicode form NFC, so that Nguyễn written as one code point and as e plus two combining marks become the same string
  • stripped of the zero-width space and the byte order mark, which are invisible and carry no meaning of their own
  • reduced to single ASCII spaces, with leading and trailing whitespace removed, so that a non-breaking space cannot hide a word from the search

The zero-width joiner and non-joiner are deliberately kept, because scripts such as Sinhala and Arabic need them to shape correctly. Two names that differ only by a joiner are therefore still two students.

A name is valid when something remains after normalizing: at least one letter or number, judged by Unicode category rather than by ASCII.

Accepted Example
Slashes Ravi s/o Kumaran, Anita d/o Rajan
Hyphens and apostrophes Siti Nur-Aisyah, Ma Ying-jeou, Sean O'Brien
Other punctuation J. R. R. Tolkien, James&, -Ahmad
Ligatures and Roman numerals X Æ A-Xii, X Æ A-Ⅻ
Any script Chinese, Japanese, Korean, Arabic, Tamil, Hebrew, Mongolian, Vietnamese
Characters outside the basic plane 𠮷田, Adlam, Cuneiform
Digits only 12345
Rejected Why
Empty, or whitespace only nothing remains after normalizing
Punctuation only, such as --- no letter or number
An emoji, or a zero-width space, on its own no letter or number

A name that holds a command prefix parses. AB3 marked its fields with the prefixes n/, p/, e/ and t/, so a name holding any of them after an ASCII space was read as the start of another field. a/l and a/p, ordinary components of a Malaysian name, failed this way until the address field was removed and the a/ prefix with it, and the rest failed until add and edit took positional arguments and command options instead. Name itself never needed changing.

Showing a long name. A card gives the name one line, shared with the tags and the follow-up pill, so a name longer than StudentCard.MAX_NAME_CHARACTERS is cut and the whole of it is left on the card as a tooltip. The count is fixed rather than taken from the room the row has left over, so the same name breaks off in the same place on every card instead of moving as the rest of the card changes. A name within the count is cut all the same where the row runs out of room, so the name goes on the card through UiText.showMiddleShortenedToFit, which hands the label the whole name on hover whenever it is drawn narrower than its text needs. The tags take that path for the same reason.

The cut is taken from the middle, keeping 13 characters of the start and 9 of the end. A cut at the close alone puts Mohamed Abdul Rahman bin Ismail and Mohamed Abdul Rahman bin Ahmad on two cards as the same text, and a reader scanning the list has nothing to tell the rows apart by; the end of a name is where two such students differ, which is what the 9 characters buy. Wrapping the name to a second line was weighed and dropped, because it lets any card grow to two lines tall and so costs the list more rows than the collision costs a reader, and the pill and the tags still have to fit beside the name. A name within one character of the count is left whole, since the ellipsis takes a place of its own and the cut would save no room. UiText counts both ends with StringUtil.firstCharacters and StringUtil.lastCharacters, so neither cut separates a letter from the accent that belongs to it nor an emoji from its other half.

Two cuts reach the name and they have to agree on where they take text from. The count is the card's own and is applied before the card is laid out, so it depends on the name alone. The second is taken once the line knows how much room it has, and so depends on what the card carries beside the name. CardName takes that second cut itself, from the middle and through the same StringUtil counting, rather than leaving it to the label. A cut at the end would read as the same text on two cards: at the window's smallest width both Mohamed Abdul Rahman bin Ismail and Mohamed Abdul Rahman bin Ahmad drew as Mohamed Abd.... A label told to elide from the middle instead cuts at a character index, which falls between the two halves of a character Java stores in two, so Alexander 𠮷田 drew as Ale… with the back half of its fourth character after it.

DarkTheme.css therefore tells .card-name to clip, so that a cut CardName gets a pixel wrong shows a glyph against the edge rather than a broken one. That belongs in the stylesheet rather than beside the cut: an author stylesheet overrides what code sets on a styleable property, so a setTextOverrun call on the label would be dropped without a word.

CardName asks for the room the whole name needs however little of it is drawn. The row shares its width out from what the name asks for, so a name that asked only for what it is drawn at would be handed less room on every pass, and the name and the tags beside it would chase each other down.

Confirming a clear

ClearCommand.execute returns a prompt containing the whole-book count, including students hidden by the current filter. It does not mutate the model. An empty book instead returns a no-op message without a prompt. LogicManager.requestClearConfirmation keeps a non-empty book's request in pendingClearCommand, an Optional<ClearCommand>, and returns before the usual storage write. Optional.empty() represents no pending request. While the request is pending, it reads the next input as a reply to the concise [y/N] prompt. Only surrounding Unicode whitespace is trimmed; internal characters are kept so a value cannot become an accepted word by removing characters from within it. Replies ignore case. Trimming scans from both ends with StringUtil.isWhitespace, retaining the command parser's Unicode whitespace rules. This takes linear time at worst; an internal whitespace run is never searched for a trailing match.

An empty reply, n, or no drops the request without executing or saving anything. Only the exact replies y and yes invoke ClearCommand.executeConfirmed and save the empty book. Words merely starting with either letter, such as yellow or nope, are invalid. Other input raises a ParseException with feedback and the prompt repeated and keeps the request pending; it is never executed as another command. If the reply handler unexpectedly has no request, it raises a CommandException asking the user to enter clear, rather than letting an unchecked exception escape. The normal presence guard prevents this case. The pending request is cleared before saving so that a storage error cannot leave a stale confirmation active. It lives only in memory, so closing and restarting TAB cannot confirm a previous request. The existing result area and command field provide the prompt and replies without a mouse or dialog. MainWindow supplies Logic.isAwaitingConfirmation to CommandBox, which submits an empty Enter only during confirmation; otherwise an empty Enter keeps its existing no-op behavior. Each Logic implementation must supply this state explicitly so a default cannot silently suppress cancellation.

[Proposed] Undo/redo feature

Proposed Implementation

The proposed undo/redo mechanism is facilitated by VersionedStudentBook. It extends StudentBook with an undo/redo history, stored internally as a studentBookStateList and currentStatePointer. Additionally, it implements the following operations:

  • VersionedStudentBook#commit() -- Saves the current state of the student book in its history.
  • VersionedStudentBook#undo() -- Restores the previous state of the student book from its history.
  • VersionedStudentBook#redo() -- Restores a previously undone state of the student book from its history.

These operations would be exposed in the Model interface as Model#commitStudentBook(), Model#undoStudentBook() and Model#redoStudentBook() respectively.

Given below is an example usage scenario and how the undo/redo mechanism behaves at each step.

Step 1. The User launches TAB for the first time. The VersionedStudentBook will be initialized with the initial state of the student book, and the currentStatePointer pointing to that single state.

Step 2. The User executes delete 5 command to delete the 5th student in the student book. The delete command calls Model#commitStudentBook(), causing the modified state of the student book after the delete 5 command executes to be saved in the studentBookStateList, and the currentStatePointer is shifted to the newly inserted state.

Step 3. The User executes add David …​ to add a new student. The add command also calls Model#commitStudentBook(), causing another modified state of the student book to be saved into the studentBookStateList.

Note: If a command fails its execution, it will not call Model#commitStudentBook(), so the state of the student book will not be saved into the studentBookStateList.

Step 4. The User now decides that adding the student was a mistake, and decides to undo that action by executing the undo command. The undo command will call Model#undoStudentBook(), which will shift the currentStatePointer once to the left, pointing it to the previous state, and restores the student book to that state.

Note: If the currentStatePointer is at index 0, pointing to the initial StudentBook state, then there are no previous StudentBook states to restore. The undo command uses Model#canUndoStudentBook() to check if this is the case. If so, it will return an error to the User rather than attempting to perform the undo.

Non-Functional Requirements

  1. Operating environment: Should work on any mainstream OS as long as it has Java 25 (64-bit) installed without requiring platform-specific installation or OS-dependent libraries. This satisfies Constraint-Platform-Independent and Constraint-Java-Version.
  2. Portability: Should be packaged as a single executable JAR file of at most 100 MB that runs directly without requiring an installer or system administrator privileges. This satisfies Constraint-Portable, Constraint-Single-File, and Constraint-File-Size.
  3. Single-user operation: Should be designed for a single user operating locally at any given time, without requiring or supporting concurrent multi-user write access to the data file. This satisfies Constraint-Single-User.
  4. CLI-first accessibility: All student management operations must be executable entirely via keyboard commands without requiring a mouse, trackpad, or other pointing device. This satisfies Constraint-Typing-Preferred.
  5. Typing efficiency: A user with above-average typing speed for regular English text should be able to accomplish regular student management tasks faster using CLI commands than using a traditional mouse-driven graphical user interface. This satisfies Constraint-Typing-Preferred.
  6. Capacity: Should comfortably store and manage up to 1,000 student records (sufficient for multiple semesters of active and archived tutorial and lab slots) without noticeable degradation in performance.
  7. Responsiveness: Should execute typical commands (such as adding, editing, deleting, tagging, listing, and filtering across up to 1,000 student records) and update the GUI within 100 milliseconds on standard modern desktop hardware.
  8. Startup time: Should launch and display the GUI, ready for user command input, within 2 seconds on standard modern desktop hardware with an existing data file containing up to 1,000 student records.
  9. Screen resolution and scaling: The GUI should render cleanly without visual clipping or overlapping components at screen resolutions of 1920×1080 and higher with display scaling at 100% and 125%, and remain functional and usable down to 1280×720 with display scaling up to 150%. This satisfies Constraint-Screen-Resolution.

Glossary

Names do have a predetermined goodness. If they are straightforward, simple, and do not conflict, then they are called “good names.”

-Xunzi

  • Active list: The student records used for current teaching work, excluding records moved to the proposed archive.
  • Address book: A legacy term found in the upstream AddressBook-Level3 project and retained here only when referring to that project's history. TAB calls its collection of student records the student book.
  • Archive: In the proposed archiving feature, the collection of past student records retained by TAB but excluded from the active list.
  • ASCII space: The ordinary space character (U+0020). This term means that exact character rather than every whitespace character.
  • Class: In the product domain, a tutorial or lab group taught by the User. This is distinct from a Java class.
  • Class tag: A tag used to identify a class.
  • CLI (Command-Line Interface): The keyboard-driven interface through which the User enters commands into TAB.
  • Command option: A separate, hyphen-prefixed token, such as -p or --phone, that identifies the value following it. The add and edit commands use options.
  • Command prefix: A marker attached to the beginning of a field value, such as p/. AB3 marked its fields with prefixes, where TAB uses options.
  • Course: An academic subject (e.g., CS2103T) taught by the User.
  • Data file: The local, human-editable JSON file (tab.json) used by TAB to store student records, distinct from preferences.json.
  • Filtered list: The subset of student records currently visible in the GUI as a result of a filter or search command (such as find or list). Commands taking an Index target records relative to this list.
  • Follow-up: An action or response that the User still owes to a student, tracked in TAB as a pending status on a student record.
  • Identity field: A field used by TAB to identify whether two records refer to the same student. Student identity is determined by normalized name. NUS Student IDs, phone numbers, and emails are searchable details, not identity keys.
  • Index: The 1-based positive integer identifying a student according to their current display position in the active/filtered list shown in the GUI, rather than a permanent database identifier or 0-based code index.
  • Mainstream OS: Windows, Linux and macOS.
  • NFC (Normalization Form C): The Unicode normalization form TAB uses to store canonically equivalent character sequences consistently.
  • Normalized field value: The standard stored form produced by StringUtil.normalizeFieldValue, allowing input that looks the same to be stored and compared consistently.
  • NUS Student ID: A unique digital identifier for every student at the National University of Singapore. TAB accepts between 1 and 32 ASCII letters and digits, such as A01234567X or E0123456. Lowercase letters are accepted and stored in uppercase.
  • Option: See Command option.
  • Person: A legacy term found in the upstream AddressBook-Level3 project. TAB's model uses Student for a student record.
  • Prefix: See Command prefix.
  • Roster: A list of students belonging to a course, tutorial group, or lab group, particularly one prepared for import into TAB.
  • Semester close-out: The end-of-semester workflow (UC08) where active student records are archived and the active list is reset in preparation for a new academic term, optionally retaining records with pending follow-ups.
  • Student book: The collection of student records managed by TAB.
  • Student record: The information TAB stores about one student, such as their name, NUS Student ID, phone number, email address, and tags.
  • TAB: Teaching Assistant's Book; the desktop student-management application described in this guide.
  • Tag: A user-defined label attached to a student record for grouping or filtering students.
  • Tag alias: A user-defined shorthand for a longer tag (such as a shortcut for a tutorial group tag), distinct from a command or shell alias.
  • User: The teaching assistant operating TAB.
  • Whitespace: The Unicode characters with the White_Space property, as matched by Java's (?U)\s: U+0009 to U+000D, U+0020, U+0085, U+00A0, U+1680, U+2000 to U+200A, U+2028 to U+2029, U+202F, U+205F and U+3000. This set excludes the zero-width space (U+200B), byte order mark (U+FEFF), zero-width non-joiner (U+200C) and zero-width joiner (U+200D). It governs CommandTokenizer and normalized field values, not every parser: top-level command parsing retains narrower ASCII-oriented rules.
