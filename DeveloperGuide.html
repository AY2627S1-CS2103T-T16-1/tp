Setting up, getting started

Refer to the guide Setting up and getting started.

TAB supports JavaFX 17.0.7, supplied by Gradle and bundled in the release JAR. Use an x64 JDK 25 without bundled JavaFX to build and test this baseline. CI tests it on Linux, macOS, and Windows. TAB also supports the course's Mac setup, Zulu JDK+FX 25.0.3, which uses the JDK's JavaFX 25 instead. A separate macOS CI job tests that setup on Apple Silicon. See the testing guide for the matching local setups.

The bundled JavaFX native libraries target x64. Apple Silicon Macs therefore need an x64 JDK running under Rosetta when using plain JDK + JavaFX 17. An ARM64 plain JDK cannot load these libraries. The course's native ARM64 JDK+FX setup supplies its own JavaFX libraries and does not need Rosetta.

Design

Architecture

The Architecture Diagram given above explains the high-level design of TAB.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of TAB's launch and shut down.

  • At TAB's launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of TAB's work is done by the following four components:

  • UI: The UI of TAB.
  • Logic: The command executor.
  • Model: Holds the data of TAB in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, StudentListPanel, SummaryPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

Two of those parts are built from controls of their own, which the Implementation chapter draws beside the behavior they support: the command box's and the student card's.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes commands entered by the User using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Student objects from the model.

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to a StudentBookParser object, which in turn creates a parser that matches the command (e.g., DeleteCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteCommand) which is executed by the LogicManager.
  3. The command can communicate with the Model when it is executed (e.g. to delete a student).
    Note that although this is shown as a single step in the diagram above for simplicity, the code can require several interactions between the command object and the Model to complete the operation.
  4. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

LogicManager writes to storage only when a command changes the student records, and puts them back if that write fails. Rolling back model changes when saving fails covers how.

Model component

API : Model.java

The Model component,

  • stores the student book's data i.e., all Student objects (which are contained in a UniqueStudentList object).
  • treats two records as the same student only when both hold the same NUS Student ID. Names are not identity keys, and records without an NUS Student ID remain distinct.
  • stores the Student objects selected by the current filter, such as search results, in a separate filtered list. It exposes this list as an unmodifiable ObservableList<Student> that the UI can observe and bind to, so the UI updates when the list changes.
  • stores a UserPrefs object that represents the User’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Note: The alternative, arguably more object-oriented, design below keeps a unique list of tags in StudentBook, and each Student references tags from that list. This lets StudentBook maintain one Tag object per unique tag instead of each Student holding its own Tag objects.

Storage component

API : Storage.java

The Storage component,

  • can save both the student book's data and the User's preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonStudentBookStorage and JsonUserPrefsStorage (one class per data file).
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)
  • never leaves a half-written file behind, and never loads part of one it cannot read. The Implementation chapter covers replacing a data file, saves from stale windows, an unreadable data file, unknown keys and malformed tags and bad preferences.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Revealing a newly added student

AddCommand includes the new student in its CommandResult, and MainWindow asks StudentListPanel to reveal that card only after Logic.execute returns successfully, so a failed save cannot scroll to an unsaved student. Scrolling leaves focus in the command box and reads the displayed list after the search-preservation rules have run. It locates the exact saved object, so an earlier record with identical details is not revealed instead, and skips a target that has left the displayed list before layout.

English numeric feedback and data-load diagnostics format with Locale.ROOT, and highlight style names lowercase with it, keeping digits and CSS selectors consistent without touching the JVM locale or student data.

Keyboard focus order

MainWindow handles plain Tab and Shift+Tab on the student page to keep one cycle: command box, student list, summary tag list, then the reply when it is visible. The student list stays one Tab from command entry even after a reply appears, Shift+Tab returns directly, and empty lists stay reachable. SummaryPanel.fxml makes the tag ScrollPane focus-traversable and the theme outlines its focus without changing its layout size. JavaFX supplies arrow and Home/End navigation for both lists and paging for the student list; SummaryPanel handles Page Up/Down from the tag viewport's height and overflow, because JavaFX's default ScrollPane pages by its arrow-key increment. The command box keeps its own Up/Down history, and help uses its own pager.

The help pager

HelpCommand returns a command summary and the existing showHelp signal. MainWindow routes that signal, F1 and the Help menu to HelpPage, which replaces the whole student page. The hidden page stays intact, so closing help restores its filter, previous result and any unfinished command; CommandBox then moves the caret to the end and clears JavaFX's automatic selection so the next keystroke continues the draft. The summary draws its command words and flag labels from the command and parser definitions. No student data changes.

HelpPage is a keyboard pager: Space/f and b move a screenful with one line of context, Enter/j and k a line, d/u half a screenful, g/G either end, and q/Esc back to commands, with PgUp/PgDn, arrows and Home/End also accepted. The reference is drawn as spans of Text in a wrapped TextFlow inside a scrollbar-free viewport that takes the remaining window height. HelpText gives each span the class its token asks for — heading, command word, option, placeholder or plain — reusing the command box's own colors, so a marker reads the same where it is described as where it is typed. A command word carrying punctuation stays plain, being named in a sentence rather than shown as syntax, and a two-letter capital such as ID is prose rather than a field. Page movement uses the current viewport and the font those spans share, so resizing and different fonts do not skip text.

A persistent footer shows progress and the navigation keys. c copies HelpCommand.USER_GUIDE_URL and confirms it there, which is how the long address is offered rather than wrapped into the reference; the reference keeps its explicit lines short enough for the minimum width. An unused typed key shows a reminder to quit help first. Letter commands are handled on KEY_TYPED, consuming q before focus returns so quitting cannot insert a stray character; Enter navigates on KEY_PRESSED and its typed newline is consumed without changing the notice or scrolling again, as is the empty typed event macOS sends for F1.

Shared parsing helpers

CommandTokenizer defines the syntax characters for both the parser and the highlighter, so quoting, escaping and attached option markers stay consistent; each keeps its own scanning loop because highlighting must also accept unfinished input. ParserUtil.parseFollowUpSelector decodes the optional follow-up state for find and edit alike. Edit runs its duplicate-option check first, then the selector, then field errors, preserving that priority. Email and ID edits share clear-or-parse handling while keeping their own validator and descriptor setter, and add and edit share StudentIdValidation.requireNoDuplicate, with edit letting the replaced record keep its ID.

Restoring window geometry

MainWindow supplies each screen's visual bounds to WindowBounds, with the primary screen first. Equal overlap therefore favors the primary screen. Restoration chooses the screen with the greatest overlap with the saved window, preserving valid secondary-screen positions, including negative coordinates. With no overlap or no saved position, it centers on the primary screen. It clamps size and position to that screen's usable area; nonpositive or nonfinite dimensions use the default size. The window minimum also yields to a smaller usable area so it cannot defeat the size correction. The normal minimum height is 400 logical pixels, leaving room for window decorations and desktop panels within the 480 logical pixels available at 1280×720 with 150% scaling. The student list and help text scroll within the remaining space, keeping the summary total, help footer and status bar visible. A window spanning adjacent displays is fitted entirely onto the selected screen, even when it was visible across both. This keeps restoration predictable when displays have different usable heights or gaps between them.

Fitting names and tags on a card

A card is a StudentCard holding a CardHeadline and a ContactRow, and the headline in turn holds a CardName and a TagRow. These four controls extend JavaFX classes directly rather than UiPart, and StudentListCard.fxml composes them.

CardHeadline prefers a readable start of the name when allocating room to tags, but yields part of that allowance for a complete tag count. The name retains space for a character from each end. When no tag chip fits, TagRow uses the shorter N tags total instead of N more…, preserving a complete count beside the name. Its tooltip still lists every hidden tag. A partial chip requires room for four characters and an ellipsis, measured in its styled font with padding, so a two-letter fragment gives way to the total. A shorter tag can still appear in full. TagRow.fittedWidth reports the space its chosen chips or count actually use, so CardHeadline returns any unused allocation to the name before laying it out. The name requests its full natural width.

Keeping contact details readable

StudentListCard.fxml puts NUS Student ID, phone and email in ContactRow, a FlowPane that reports the natural width of one unwrapped row. This lets the containing boxes measure height at the allocated width on both JavaFX 17 and 25, rather than reserving rows based on a fixed preferred wrap length. Labels keep their preferred widths and share a line when they fit; a label that does not fit the remaining space moves to the next line. Each label's maximum width follows the pane's width, so a value longer than an entire line shrinks with an ellipsis instead of overflowing the card.

This keeps ordinary cards compact while allowing crowded cards to grow by only the rows they need. UiText.showToFit gives all three fields their full values on hover when clipped, and removes the tooltip when widening makes it unnecessary. Absent optional fields remain unmanaged, reserving no space. The follow-up pill shares an HBox with CardHeadline inside the details container, so it reserves width only on the headline. Contact rows use the same width with or without a flag. The details clip prevents drawing outside the card.

StudentListViewCell measures preferred height at the smaller of the cell's content width and the card's maximum width, matching the width used by its skin during layout. Measuring at the wider cell width would miss a wrapped contact row near a wrap threshold and squeeze the headline.

Coloring the command line

CommandBox owns a CommandHistory, a CommandTextField and a HighlightedTextOverlay. The overlay is what calls the static CommandHighlighter.highlight method to color the input, which leaves CommandBox with running the command, recalling earlier ones and marking a failure.

CommandTextField converts separators to spaces during text replacement, before JavaFX filters control characters, asking StringUtil#isWhitespace the question the tokenizer asks of each character. Otherwise the box could hide a boundary the parser reads: JavaFX deletes a vertical tab or form feed with the other control characters, and draws a line, paragraph or next-line separator with no width, each joining the words around it on screen. Pasted word boundaries survive while the command stays on one line, including when a paste replaces a selection, and CRLF counts as one separator.

CommandHighlighter breaks a command where the parser breaks it, which the User Guide invites the User to rely on. Two splits therefore cannot follow the value rule. StudentBookParser ends the command word at the first separator whatever the quotes, so add"Ravi s/o Kumaran" is the command word add"Ravi and two words after it; the value rule would draw one bold quoted word and then report an unknown command the colors never showed. FlagTokenizer reads --tag="Lab 3" as an option and a value, so the marker and equals sign take the option color and the rest its value color. A marker holding a quote or backslash is left whole, because either moves the equals sign the parser counts to.

A TextField cannot color its own content, so CommandBox keeps the field for input and hands HighlightedTextOverlay the nodes that draw a colored copy behind it, with the field's own text transparent. The overlay owns that copy, the caret and the selection band. The field still takes every keystroke and still decides which character a click lands on, so editing is unchanged.

CommandHighlighter returns spans covering every character. It walks the command itself rather than calling CommandTokenizer, which removes quotes and may refuse an unclosed one that is merely half-typed, but asks the tokenizer the questions the two must agree on — CommandTokenizer#isEscapable and StringUtil#isWhitespace for where a token ends. It rejects nothing: a command is colored while still half-typed. The copy measures its width from the whole shaped TextFlow, rounded up so it cannot wrap at a fractional pixel, and ordinary value words share a text node with their spaces so splitting an unquoted right-to-left name does not change shaping or click positions.

Three things must then agree with the field, because the User reads the copy but interacts with the field.

  • Scroll offset. The copy is drawn wherever the field draws its own text, read from the field's text node rather than recomputed. A field scrolls by rules that differ between typing, deleting, cutting and undoing, and a copy even a pixel out of step shows one character where the field hit-tests another. Reading the node once is not enough, because the skin re-scrolls after a delete, a replace or a width change, which is after the caret and the text have settled; the copy follows the node's own position. It is the node the field is drawing in, since an empty line shows the prompt in a node of the same kind that the field hides rather than discards.
  • Caret. The field's caret is drawn in its transparent text color, so the line carries one of its own, sized from a run of the text. Its position follows the primary caret shape of the field's text node, including the leading/trailing bias at script boundaries, because logical prefix widths cannot locate RTL insertion points.
  • Selection. The field's own highlight broke into fragments behind the copy, so it is disabled in the stylesheet and drawn here from a TextFlow.rangeShape path, which covers each visual segment including selections that cross RTL/LTR boundaries.

Every color the line uses is held to 3:1 against the selection band, so selecting a command cannot hide half of it. That is below the 4.5:1 WCAG asks of text this size, deliberately: on a window this dark, a band light enough to be seen against the line sits at 2.2:1, and reaching 4.5:1 against it would mean moving every token color towards white, away from the palette the mockup sets. Worth revisiting if the palette changes.

Recalling session commands

CommandBox records each submitted command in the CommandHistory it owns, before execution, so rejected commands can be recalled too. While clear confirmation is pending, replies are excluded because they cannot be reused as standalone commands; the navigation position resets without recording the reply. The helper stores submissions separately from the draft captured when Up first leaves the newest position. Down past the newest submission restores that draft. Up skips the newest submission when it already matches the text in the box and an earlier entry exists. Blank submissions and consecutive identical submissions are skipped; editing a recalled entry does not alter stored text.

The command box consumes unmodified Up/Down key presses before the text field handles them. Recalled text uses the existing text listener for coloring, and the caret moves to its end. This UI state is session-only and never enters the student model or persisted data.

Summarizing the list

SummaryPanel shows the flagged count, a count per tag and the total, beside the list. It counts Logic#getFilteredStudentList(), which is the only list Logic exposes, so it summarizes what the list is showing rather than the whole student book: after find -n Alex it counts the matches. That is the reading the User Guide documents, and it keeps the panel answering the same question as the list it sits beside. Summarizing the whole book instead would need Logic to expose it.

The list is an ObservableList, so a listener keeps the counts current without the panel being told when a command changes anything. The counting itself is static and takes a plain List<Student>, so it is tested without a toolkit; only the rendering needs one.

Tags counted the same are listed alphabetically ignoring case, because a reader does not read Zoo as coming before apple.

Case variants of one tag are counted as one tag, because that is what tag makes of them when it refuses a tag a student already carries: a reader looking for the size of tutorial group T1 would otherwise have to add up a row per spelling. The row is named with the spelling most of its students carry, which is settled by the counts rather than by the order of the list, so narrowing the list does not read as a second tag appearing.

The panel groups two spellings with String.CASE_INSENSITIVE_ORDER, which calls them equal exactly when String#equalsIgnoreCase does, and so exactly when TagCommand refuses the second of them. Folding case by lowercasing would answer a different question and split a group tag has already joined: a Greek capital sigma lowercases to a medial sigma, while the final sigma a student may carry the same tag under lowercases to itself.

Replacing a data file without losing it

FileUtil.writeToFile protects an existing JSON file from a partial save. It resolves an existing symbolic link to its destination, so replacing the saved data leaves the link in place, and rejects an unresolvable link without replacing it or creating its missing target. It also refuses a destination that is not writable, and copies an existing file's POSIX permissions to its replacement. The new contents are written and forced to a temporary file beside the real destination before an atomic move replaces it. Keeping both files in one folder is what makes the atomic move possible, and also means the folder must allow temporary-file creation. If writing or moving fails, the previous file remains unchanged and TAB removes the temporary file where it can. FileUtil creates only missing parent directories before writing the temporary file and never pre-creates an empty destination, so a failed first save preserves the absence of a book and allows normal sample-data startup. This applies to student-book and preference writes alike. On POSIX filesystems a new file keeps the temporary file's owner-only permissions, and an existing file keeps its own.

JsonStudentBookStorage reports a data-folder or file collision and a save-lock failure at the operation boundary, where the failing path and its purpose are known. It preserves permission exceptions for the existing permission-specific feedback and never removes an obstructing file or folder. Logic rolls back records and the filter after these failures just as it does for other save errors.

StorageManager logs read and write attempts and successful saves at FINE, preference-file operations included. An entry identifies the file path without copying student or preference contents, and a save is logged as complete only after the storage delegate returns successfully.

Protecting saves from stale windows

JsonStudentBookStorage retains a separate copy of the student book loaded or successfully saved at each path. Before saving, it rereads the current records and compares them with that snapshot. A difference, a removed file, or an unreadable replacement refuses the save; LogicManager then restores records and the active filter. The snapshot advances only after a successful save. Comparison uses parsed student records, so harmless JSON formatting changes do not create a conflict. Each normal application startup reads the file before issuing commands; callers saving without a prior read adopt the on-disk book as their initial baseline.

The comparison and replacement share an operating-system lock on .tab.json.lock beside the real destination. Resolving symbolic links makes windows reaching the same destination share a lock. A busy lock refuses the save with retry guidance. The sidecar remains after closing TAB: deleting it could allow different processes to lock different files with the same name. Closing its channel releases the lock, including on a failed save or process exit. This prevents stale TAB windows from overwriting each other's records; it does not add concurrent multi-user editing. External editors do not honor this lock and must be used with all TAB windows closed.

Rolling back model changes when saving fails

LogicManager takes a copy of the student book and its active display filter before executing a command. It compares the resulting student book with that copy and writes to storage only when student records changed. Commands such as list, find, help, and exit can therefore run even when the data file is not writable.

When a write fails, LogicManager restores both the student-book copy and the previous filter before reporting the storage error. Restoring the filter as well as the records matters because add normally resets the display to show every student. The failed command consequently has no visible or in-memory effect, and retrying it cannot apply the same change twice. A confirmed clear follows the same save-and-restore path; its pending confirmation is still removed before the save attempt so that a failure does not leave a stale reply active.

Resolving application file locations

AppUtil#getApplicationDirectory uses the code-source location to distinguish a packaged JAR from an exploded Gradle or IDE build. A packaged application stores data/tab.json, preferences.json, and tab.log.* beside the JAR regardless of the process's working directory. An exploded build keeps the working directory as its application directory, preserving the development workflow.

How commands read their arguments

A command marks each field with an option rather than a prefix attached to the value:

add NAME [-p PHONE] [-e EMAIL] [--id NUS_STUDENT_ID] [-t TAG]... [--follow-up]
edit TARGET [-n NAME] [-p PHONE] [-e EMAIL] [--id NUS_STUDENT_ID] [-t TAG]... [--follow-up | --no-follow-up]

Aspect: how a command tells one field from the next

  • Alternative 1 (current choice): an option, a whole token of its own, such as -p or --phone.
    • Pros: a value is read as a value whatever it contains, so a name may hold any character.
    • Cons: a value with spaces has to be quoted, and the User types a space between the option and its value.
  • Alternative 2: a prefix joined to the value, as AB3 uses, such as p/91234567.
    • Pros: shorter to type, with no quoting.
    • Cons: a prefix has to be a sequence no value ever contains, and no such sequence exists for a name. s/o, d/o, a/l and a/p are ordinary parts of Singaporean and Malaysian names, and a/l was unreadable for as long as an address field was marked a/. Widening the prefixes moves the collision rather than removing it.

Each value option has a long alias: --name, --phone, --email and --tag answer to -n, -p, -e and -t. add takes its name in the preamble; edit and find both read -n/--name.

edit names its target in the preamble or with --target-id NUS_STUDENT_ID; a target option of its own keeps selection unambiguous while --id sets or clears the ID field. Selecting a student covers the targets edit, tag and delete share.

Parsing runs in two passes, the way a shell does it.

CommandTokenizer splits the arguments. Whitespace separates tokens and double quotes group a value that contains it. Straight, curly and full-width quotes are interchangeable delimiters, including in mixed pairs, so input methods and pasted documents are accepted; CommandTokenizer#isQuote shares that rule with the highlighter, and every supported quote can be escaped to keep it literally. A backslash escapes a quote or another backslash, and before anything else stays in the value, so nothing the User typed disappears unasked. Each token records whether a quote took part in it, which is the only thing separating the value -Ahmad from the option -e.

An option where a value was expected is read as the option before it having been left empty: add John -p 123 -t -e reports that -t needs a value rather than storing -e as a tag. A value that really opens with a hyphen is quoted.

FlagTokenizer sorts the tokens into options. Tokens before the first option are the preamble, joined with single ASCII spaces, and each command reads it as whatever it takes there — the name for add, so a multi-word name needs no quotes, and the index for edit. Each command names its own through AddCommand.FIELD_NAME and EditCommand.FIELD_INDEX rather than leaving it to the shared CliFlags.

Kind Behavior
Value-taking (-n, -p, -e, --id, -t) takes the token after it, or a value joined by =. -t/--tag repeats for add and edit; tag takes exactly one through -a/--add or -r/--remove.
Presence-only (--follow-up/-f, --no-follow-up/-nf) records an empty value and consumes no token, which lets FlagArgumentMap tell an absent option from a present marker without a second representation. add accepts only --follow-up, edit both to set or clear, find both to filter. An attached value on one is refused specifically.

Each short and long marker resolves to the same CliFlag, so mixed aliases for a single-valued field are duplicates rather than independent fields. NUS Student ID uses --id as its canonical option with the otherwise unused -i as a typing-friendly alias; giving both is rejected as a repeated field rather than letting one silently override the other, and usage labels and messages use the canonical spelling. Duplicate-option feedback names the repeated markers rather than values, since presence-only options have none, and FlagArgumentMap keeps the first spelling supplied.

An attached value splits on the first = only, so later ones stay in the value, and it is unambiguously part of its option when it opens with a hyphen. An empty attached value must be quoted, as --tag="", so an accidental --tag= cannot clear data. Because CommandTokenizer records whether a token began with a quote, a fully quoted "--tag=T1" stays a value while the quote in --tag="Lab 3" does not hide the marker.

For edit, tag values are normalized before validation. One normalized blank clears every tag, including when the input holds Unicode spaces; a blank beside other tag values is refused with an explanation that clearing needs the blank on its own; and non-blank values are still validated, so every problem is reported without tags being discarded silently.

add keeps its name before the options. If the tokenizer refuses -n or --name, AddCommandParser adds a placement hint to the error, and a missing name gets the same hint, so a User who knows edit's name option recovers at once.

The shape of the command is settled before any field is read. An unclosed quote, an unknown option, or a single-valued option given twice — including once under each alias — each leave it unclear which field a value belongs to, so each is refused on its own rather than collected with the field errors. An unknown option names its marker without echoing an attached value, and a missing value and a token belonging to no option are each reported for what they are.

edit clears a field with an explicitly empty value rather than with a bare option. -p "" removes the phone number, -e "" removes the email, --id "" removes the NUS Student ID, and -t "" removes every tag. Phone, email and NUS Student ID values are trimmed before this check, so quoted whitespace clears any of those optional fields too. A bare option cannot mean "clear" here, because a bare option is what reports the mistake in edit 1 -t -e a@b.com: the -e is read as the value -t was left without, rather than being stored as a tag. An empty quoted value also separates a value left empty by accident from one cleared on purpose. CommandTokenizer produces an empty token for "" and leaves the decision to the field parser, so no tokenizer change was needed.

edit sets follow-up with --follow-up (alias -f) and clears it with --no-follow-up (alias -nf). The parser rejects contradictory options before describing any edit, so neither the model nor the saved book changes on that error. The -nf alias makes clearing quick to type without making opposite actions differ only in case, as -f and -F would. Both clear spellings map to the same option, so mixing them is also detected as a duplicate.

Selecting a student

edit, tag and delete each take a target: a displayed index, a letter-leading NUS Student ID, or an explicit option. That option is --target-id for edit, whose --id sets the ID field instead, and --id (alias -i) for tag and delete. Either form builds a StudentTarget, through ParserUtil.parseRequiredStudentTarget for a preamble target or ParserUtil.parseNusStudentId for an explicit one; tag keeps ParserUtil.parseRequiredIndex for a numeric preamble.

The explicit option admits a digit-leading ID without changing how a bare number selects a displayed position, so an in-range number stays an index even when another record holds the same numeric ID. Repeating the option, or giving a preamble target and an explicit one together, is refused rather than guessed at, and selecting a target does not count as a field edit.

An index resolves against the displayed list and an ID across the whole book. A roster ID therefore reaches a student a search has hidden, and a search predicate survives an edit.

Diagnostics keep the spelling the User typed. ParserUtil.parseIndex separates malformed or non-positive input from a positive integer beyond the supported range, and StudentTarget reports an out-of-range position with that spelling and the current displayed count, zero included. A non-positive or non-integer target keeps the concise positive-integer reason alongside any field errors, and delete adds the explicit --id form whenever the refused target reads as a valid NUS Student ID — spelling intact, so a stored numeric ID keeps its leading zeroes. edit and tag share FlagTokenizer.tokenizeWithIndex, which reports an unquoted negative number as both an invalid index and an unknown option, and each reports a value following an otherwise valid target. The retained spelling affects diagnostics only, not target equality or hashing.

Adding or removing one tag

TagCommandParser reads tag TARGET -a TAG (alias --add) or tag TARGET -r TAG (alias --remove) with the existing FlagTokenizer and ParserUtil. The option names the action: both spellings of each map to FLAG_ADD_TAG or FLAG_REMOVE_TAG. Exactly one action option is accepted, so a conflicting pair and a repeated option are both refused, and ParseProblems collects every target and tag error before a command is built. A tag syntax failure and a missing action option each carry guidance for addition and for removal.

TagCommand compares normalized tag names ignoring case, then copies the existing tag set and constructs a replacement student with every other field preserved. TagCommand.Action selects addition or removal while sharing target resolution, matching, student replacement and feedback. The search filter stays active, so removing a tag that filter uses may hide the student from the displayed list.

Case variants of one tag name fold together. ParserUtil.parseTags folds them in add and in edit's replacement tags using String.CASE_INSENSITIVE_ORDER, matching the tag command and the summary, while ParseProblems retains input order so the first spelling wins and every invalid tag still gets a diagnostic. JsonAdaptedStudent applies the same ordering after validating and normalizing stored tags, keeping the first spelling in the JSON array, so loaded cards and tag summaries agree and the next successful save writes one tag per group. Tag equality itself is unchanged. Removal takes every matching variant of the requested group and leaves unrelated tags alone. Duplicate and successful removal feedback quote a matching stored tag's spelling — the first in the card's tag display order when several variants match. A general tag named Needs follow-up stays separate from the follow-up flag, though the parsers no longer let one be added.

For a hidden flagged student, the absent-tag hint supplies edit --target-id NUS_STUDENT_ID --no-follow-up with the student's stored ID. This addresses even digit-leading IDs without changing the active search.

Commands with no arguments

StudentBookParser rejects non-whitespace input after clear, list, help, and exit before returning a command. Its existing Unicode whitespace rule accepts pasted whitespace as well as spaces and tabs. The feedback names the command and unexpected input, with long input shortened to keep the reason visible. Quotes do not make an argument absent: clear "" is refused too. A parse failure reaches neither command execution nor LogicManager's storage write, so it preserves both the displayed list and the JSON file.

Invisible characters on the command line

Before the command word is read, StudentBookParser strips the same Unicode format and non-whitespace control characters that StringUtil.normalizeFieldValue strips from a stored value, through StringUtil.stripFormatCharacters. Whitespace controls such as tabs and line breaks remain separators rather than joining adjacent words. A direction mark or a zero-width space pasted before a command word or an index is otherwise a word that looks right but matches no command, or an index reported as not a positive integer. The zero-width joiner and non-joiner are kept, because a script such as Sinhala needs them to shape a word, and a command word holding one is a different word rather than the same word with a character removed.

Reading a command word in any case

StudentBookParser folds the first word of the input to lower case before it dispatches, so List, LIST and list all reach ListCommand. No two command words differ only in case, so a capitalized word can only mean the one command, and refusing it over a Caps Lock left on or a Shift held a moment too long costs the User a retyping for nothing.

The fold is CommandWords.foldCase, which CommandWords.suggestFor applies to the word it measures as well. Dispatch and suggestion therefore agree by construction, where a second fold written into the parser could come to differ from this one, leaving a word that is refused and then suggested back to the User unchanged. The fold is Locale.ROOT's rather than the User's, whose Turkish rules would turn LIST into a word with a dotless ı that answers to nothing.

The first word alone is folded. The arguments reach the command parsers as typed, so Find -n Alex searches for Alex with its capital and Add John Doe stores the name as it was written. Option spellings stay case-sensitive, as the User Guide documents them: an option is read among the values rather than in front of them, so folding there would have to leave the values it sits beside untouched, which is a decision of its own. The typed word is kept beside the folded one, because an unknown word is quoted back in the case it was typed in, while a command refusing arguments names the command: LIST oops reports that list takes no arguments.

Suggesting a command word

A word TAB does not dispatch on is answered with the word as typed and the command words it is a likely attempt at. CommandWords asks two questions in order.

What does the word open? A part-typed word is right as far as it goes, so del stands for delete even though help is nearer by edits, at two against three. Only a word that opens nothing is measured at all.

What is it near? StringUtil.editDistance counts insertions, deletions, substitutions and swaps of neighboring characters. A swap costs one edit because a fast typist makes them as readily as the rest; otherwise lsit would sit two edits from list, as far as a wilder guess. The budget is two edits for every command word whatever its length, which is what the user story asks for and what reaches the slips a teaching assistant makes: ls is two insertions short of list, dlte two deletions from delete.

Two edits also reach past a short command word's first letter, which is how dlt came to be answered with edit. A measured word must therefore open with the character the command word opens with, unless the single edit between them is that character — which keeps felete, edlete and elete reading as delete. The first letter is the one a typist is least likely to get wrong.

Every equally likely word is named, in the alphabetical order of COMMAND_WORDS: eit is a letter short of both edit and exit, and answering with one alone would read as knowledge TAB does not have. Past three the reply falls back to the pointer to help, since a list that long says only that TAB cannot tell. No typed word reaches that today, edit and exit being the only pair sharing a first letter; the limit is there for command words TAB may gain.

Comparison folds case with the CommandWords.foldCase the parser dispatches with, so Delte reads as delete, while a correctly spelled word in any case is dispatched before reaching here. The reply quotes the word as typed, so a User who typed capitals can recognize what they did, shortened the way a rejected field value is. Lengths are compared before distances, which settles a pasted line against every command word without measuring it.

A suggestion is never run: dispatching delete for dlte would act on a word the User did not type, and a wrong guess there costs a student record where a wrong suggestion costs a line of text. StudentBookParser raises the same ParseException as for any unknown word, leaving the model, the saved file and the typed text as they were.

The parser dispatches from a switch rather than from COMMAND_WORDS, so the two could disagree and a word missing from the list would work while being suggested to nobody. CommandWordsTest resolves the command words out of the parser's own cases and compares them against the list.

Follow-up flag

FollowUpFlag extends Tag and uses its validation, normalization, and display behavior. Its fixed name is Needs follow-up. A general tag with those words remains a distinct value: tag equality requires the same concrete class as well as the same normalized name. ParserUtil.parseTagToAdd and JsonAdaptedTag.toModelType both refuse that name however it is spelled, so that a card cannot show the same label as a tag and as the marker whether the value arrives from a command or from a hand-edited file. A file written before the rule stops loading, with an error naming the record and the field to correct. Tag itself still accepts the name, so removal reads it as an ordinary tag and TagCommand keeps explaining that the marker is what a flagged student carries. Student holds an optional FollowUpFlag and exposes it through getFlag(); isFlagged() preserves the existing boolean interface for commands and the UI. Full equality and hashing include the flag, but isSameStudent does not: changing whether a student needs a reply does not change their identity. The flag is stored as Optional<FollowUpFlag>; the constructor without a follow-up argument defaults to Optional.empty().

Tag searches match ordinary tags as parts of their inherited tagName values, ignoring case. Follow-up status is selected independently through -f or -nf, so its displayed label never produces a text-field match. The student card and command feedback display the same value, while the card keeps the flag at the trailing edge of its headline.

The add parser maps the presence of --follow-up, or its -f alias, to true. For edit, the EditStudentDescriptor stores a nullable Boolean isFlagged: null preserves the existing state, true sets follow-up, and false clears it. getFlagged() exposes this as an Optional<Boolean>. EditCommand uses the requested value when present, otherwise the selected student's existing state. This makes either request safe to repeat while preserving follow-up during unrelated edits. Descriptor copies and equality retain all three states.

JsonAdaptedStudent uses a nullable Boolean flag at the storage boundary. Only Boolean.TRUE creates a FollowUpFlag in the model; a missing key, JSON null, and false all map to no flag. When saving, a present flag is written as "flag": true, while an absent flag is represented as null and omitted by Jackson's NON_NULL policy. Files created before the field existed therefore load without migration or gratuitous rewrites. JsonFollowUpFlagDeserializer accepts only JSON Boolean tokens, with Jackson retaining null for a missing or null key. Rejecting other token types before Jackson can coerce them prevents numeric hand edits from silently changing follow-up status. The normal loading-error path identifies the record and flag, blocks startup, and preserves the file.

StudentCard shows a Needs follow-up label for true. For false it makes the label both invisible and unmanaged, so the card keeps no blank placeholder row. Successful add, edit and delete feedback formats student records consistently with the student card: optional fields (NUS Student ID, phone, email, tags, follow-up status) appear only when present, with tags ordered alphabetically ignoring case, avoiding placeholder labels or empty tag markers.

Field values

Two decisions shape every field a student carries.

A detail TAB does not know is absent, not blank. Student holds phone, email and NUS Student ID as Optional<Phone>, Optional<Email> and Optional<NusStudentId>, and no Student field is ever null. Both constructors require non-null arguments, one taking the follow-up boolean and the other defaulting to unflagged for sample data. Add, edit, storage conversion and the test builders all pass optionals into that contract, so nullable strings stay inside the storage adapter and the file format is unchanged.

Two values that look the same are stored the same. Name, Tag, Phone, Email and NusStudentId each keep the form StringUtil.normalizeFieldValue returns. That strips characters the reader cannot see, such as direction marks left by a copy and paste; collapses each run of spaces to one and trims the ends; and finally composes the result, so that a letter typed as a base plus a separate accent is stored as the single character it looks like. Composing comes last because an invisible character between the two blocks them from joining. The composed form is Unicode NFC.

Aspect: how long a phone value may be

  • Alternative 1 (current choice): no maximum, with the minimum of three Unicode decimal digits still applying.
    • Pros: a teaching assistant can record several numbers, extensions and contact annotations in one field, and no saved record becomes unloadable.
    • Cons: a 400-digit value is accepted. A long value is shown with an ellipsis and its full text on hover, rather than the stored text being cut.
  • Alternative 2: a fixed cap, as Email has at 254 characters.
    • Pros: bounds what the card and the file have to hold.
    • Cons: rejects useful contact details, and a cap below an existing value stops that record loading. Email's limit answers its own validation and storage concerns and does not transfer.

Worth revisiting if a concrete problem appears, with a migration plan for existing data and a limit justified by contact use cases.

What differs is the rule each field enforces, and why it may be missing.

NUS Student ID. Between 1 and 32 ASCII letters and digits, stored uppercase, so e0123456 and E0123456 are one value. The range covers the identifiers issued to different groups of students while stopping an accidentally pasted value from hiding the rest of a card. NusStudentId.getFailureReason performs the single validation scan and isValidNusStudentId delegates to it, keeping the accepted format and the user-facing error in step without a second regex.

Email. Email accepts the RFC 5322 unquoted dot-atom local part, so addresses with apostrophes, repeated symbols or trailing underscores can be recorded; only dots require non-empty groups on both sides. Quoted local parts and domain literals stay unsupported. A student is recorded before an address is known rather than one being invented.

Email.MAX_LENGTH caps an entered address at 254 characters, and both ParserUtil and JsonAdaptedStudent check it before calling the matcher. The bound is not there to simplify validation. VALIDATION_REGEX nests a quantifier inside another, and Java matches a repeated group by recursion, one frame per repetition, so an address with enough .-separated groups exhausts the stack. StackOverflowError is an Error no parser catches and CommandBox catches only CommandException and ParseException, so the User saw nothing at all. 254 is the limit RFC 5321 section 4.5.3.1 puts on a forward path, so the bound comes from the domain; it is also the longest measured to be safe on every stack size tried, where a 513-character address overflows a 256 KB stack. isValidEmail itself keeps no length limit, so each input boundary reports length and format failures separately, and a saved address up to 254 characters loads while a longer one raises IllegalValueException with its actual and allowed lengths.

Phone. A class roster can give a name, an ID and a university email without a personal mobile number. Phone is neither an identity field nor a key: two students may hold the same number or none, and isSameStudent reads neither case. It is normalized only so that a number typed with unusual whitespace, or wrapped in the invisible marks a chat app puts around a copied one, is stored consistently.

Messages.getErrorMessageForInvalidValue shortens a rejected value past MAX_QUOTED_VALUE_LENGTH characters so a very long one cannot push the reason out of view. It counts characters through StringUtil.firstCharacters, as a reader counts them, separating neither an emoji nor a letter from its accent; a student card cuts a name or tag with the same helper. Command parsing and storage share that message, so both report an invalid value the same way.

A name is displayed and searched as text but is not an identity field, so several students may hold the same normalized name. Name keeps the normalized form described above, with one exception: the zero-width joiner and non-joiner survive, because scripts such as Sinhala and Arabic need them to shape correctly. Two names differing only by a joiner are therefore two students.

Detecting duplicate students

NUS Student ID is the sole identity key. Student.isSameStudent returns true only when both records hold equal NUS Student IDs. Because construction normalizes letters to uppercase, this comparison is case-insensitive. A shared name does not establish identity, and neither does a shared phone number or email. Records without an NUS Student ID therefore remain distinct even when their other details match. UniqueStudentList applies this rule to add, edit, and model replacement, so command execution and storage loading enforce the same contract.

When add or edit finds a matching NUS Student ID, it rejects the operation without mutation and names the normalized ID and student who already holds it. During storage loading, JsonSerializableStudentBook admits repeated names but rejects a repeated NUS Student ID with both record numbers, both names, and the ID. This keeps hand-edited files diagnosable while allowing common names in a class.

A matching student appears at the end of the results without changing earlier indexes. EditCommand first compares the prospective record with the selected one by full equality. An unchanged edit returns an explicit no-change response before any duplicate check or replacement, so the filter survives and the list is not notified for nothing; LogicManager still skips saving an unchanged book.

After the identity check succeeds, LikelyDuplicateWarning compares the prospective record with every existing student. Name and email comparisons ignore case; names already carry normalizeFieldValue's whitespace normalization. Phone search and warnings share Phone.normalizeDigits, which removes non-digit characters and converts Unicode decimal digits to ASCII. Warnings require equality of the complete digit sequence; search permits substrings. Country codes and extension digits remain significant, while the stored number retains its formatting. Absent phones and absent emails do not match: two records that both lack the detail share no value, so neither is offered as evidence of a duplicate.

The commands collect the warnings before mutation and set them off from the success message with a blank line. Matches group by field under one labeled WARNING: Possible duplicate student line, each naming at most two students and summarizing the rest as N others, so a shared placeholder cannot fill the result box. The review advice appears once, after every matching field. A phone warning omits the parenthetical value, because matched records can store the same digits with different formatting and no one spelling would represent them all.

EditCommand compares only name, phone, or email values that differ from the selected record. It excludes the selected Student instance but still uses the complete unfiltered student book, so a filtered list cannot hide a match and unrelated tag or follow-up edits do not repeat an acknowledged warning. Name comparisons share StringUtil.normalizeNameForComparison with name searches: Latin accents and straight/curly apostrophe differences are ignored, so copied roster names can be found or flagged using ordinary keyboard input.

All of this is advisory: these comparisons never feed isSameStudent or the storage duplicate check, so they cannot reject or discard a legitimate shared detail.

Finding students

FindCommandParser uses FlagTokenizer and the existing CliFlags aliases for name, NUS Student ID, phone, email and tag. Every search term must have a field option. An option takes one word or one double-quoted phrase; apostrophes are literal characters, so names such as O'Brien do not need quoting. Repeated options retain all values. Bare terms receive MESSAGE_UNQUALIFIED_TERM, and an extra bare word after an option receives the shared tokenizer's unexpected-value diagnostic. Empty or whitespace-only values receive MESSAGE_EMPTY_KEYWORD; unterminated double quotes report CommandTokenizer.MESSAGE_UNCLOSED_QUOTE.

Search terms are normalized with StringUtil.normalizeFieldValue, collapsing whitespace runs and applying Unicode NFC normalization. The parser creates a DetailsContainsKeywordsPredicate with terms grouped by its Field enum. Every term must match its selected field, using case-insensitive substrings: AND applies both within and between fields. Each tag term must occur within one tag, but separate terms may match the same tag or different tags. Absent optional fields do not match. Explicit field selectors prevent unrelated matches in other details and replace the earlier unqualified OR search. Follow-up status is selected with the presence-only -f/--follow-up and -nf/--no-follow-up options. The predicate holds an Optional<Boolean>: empty imposes no status restriction, true requires follow-up, and false requires its absence. A status-only search is valid, and combinations require both the status and every field term. The parser rejects conflicting or repeated status options before execution, matching the existing edit rules.

Case comparison folds each Unicode code point independently using Character.toLowerCase(Character.toUpperCase(...)), avoiding context-sensitive whole-word lowercasing of Greek final sigma. Tag searches therefore agree with the case comparison used by TagCommand. Name comparison additionally applies canonical decomposition and removes marks attached to Latin letters, then maps curly apostrophes to straight ones. Marks in other scripts remain significant, so vowels needed to distinguish names are retained. This is a comparison key, not transliteration; model values and JSON retain their existing spelling.

A phone term made only of Unicode decimal digits, or of those digits with grouping whitespace and phone punctuation (+, -, (, ), .), is also compared with non-digit characters removed and each decimal digit mapped to its ASCII equivalent by numeric value. So 91234567, 9123-4567 and "9123 4567" all match +65 9123 4567 or 91234567, and a copied grouped number needs no reformatting; a query carrying a country code still requires those digits in the stored phone. Normalizing both sides lets ASCII, full-width and other Unicode decimal digits match each other, including digits written as supplementary code points, so "９１２３ ４５６７" matches 91234567. The fallback applies only when a digit survives normalization, which keeps a punctuation-only term from matching every phone and leaves an annotation such as "ext 21" matching literally. Unicode whitespace follows the same rule as field normalization, and the allowed-character check uses a possessive quantifier so a long term scans without backtracking. Stored student details and saved data do not change.

Both FindCommand and ListCommand report how many students are displayed. FindCommand counts the matches through Messages.getStudentsFoundOverview, which distinguishes Found 0 students., Found 1 student. and Found <n> students.; ListCommand counts after resetting the filter, giving Listed 0 students., Listed 1 student. or Listed <n> students..

Handling an unreadable data file

Startup distinguishes a missing student-book file from an unreadable one. A missing data/tab.json is a first launch and receives the sample student book. An existing file is first parsed as JSON and then every student record and field is converted to its model type. Both stages finish before the normal UI can accept a command.

JsonUtil.readJsonFile therefore reports a file as missing only once its absence is established, using Files.notExists. Files.exists answers false both for a file that is not there and for one whose folder cannot be opened, and MainApp.initModelManager reads a missing file as a first run, so a folder TAB merely cannot open would open the window on sample students in place of records it was never able to read. A file whose existence cannot be determined is read instead, and the access failure reported like any other.

The records themselves are already safe from that mistake. The baseline JsonStudentBookStorage records for an unreadable folder is Optional.empty(), so once access is restored saveIfUnchanged finds a book on disk that the window never loaded and refuses the save. What is left without this check is a window opened on sample data that then refuses every save as stale, telling a User who changed nothing to close it and restart. Reporting the access failure at startup replaces both with the reason.

JsonUtil enables Jackson's strict duplicate-key detection and checks for another token after reading the root value. A repeated key or trailing value would otherwise silently lose data on the next save. Both are rejected through the existing loading-error path, with the key or offending token's location; whitespace after the document and keys reused in separate objects remain valid.

FileUtil.readFromFile decodes UTF-8 strictly and removes only an optional leading BOM before JSON parsing. This accepts files saved by editors that add a BOM while rejecting malformed byte sequences rather than silently replacing letters with U+FFFD. JsonUtil translates decoding failures into an encoding explanation and recovery guidance through the same DataLoadingException boundary; startup preserves the original bytes and blocks the normal UI.

JsonUtil turns malformed JSON or an incompatible JSON shape into a DataLoadingException, and JsonParseErrorFormatter words the explanation it carries. For a syntax error the formatter takes the deepest parser exception that has a usable location, so the reported line and column point at the offending token rather than the last value mapped successfully, and it pairs that concise explanation with the affected line and at most one line on either side. Source lines are capped at 160 characters, an affected long line cropped around the reported column, which keeps minified JSON useful without filling the dialog. Without a usable location the formatter omits the source rather than falling back to Jackson's source-bearing message. During model conversion, JsonAdaptedStudent identifies the invalid field and JsonSerializableStudentBook adds the one-based record number and, where it has one, the name. JsonStudentBookStorage carries that explanation through the same DataLoadingException boundary.

MainApp records the loading error and creates an empty model only as an internal placeholder, so shutdown stays safe, then hands the error to UiManager. UiManager checks for it before constructing MainWindow, and on finding one shows an error dialog with the data-file path, the specific reason and recovery guidance. Closing that dialog closes TAB, because the normal window never opened, so no command — exit included — can save the placeholder over the unreadable file.

Failing closed was chosen over displaying a partial or read-only student book, because it keeps recovery small and unambiguous: the User repairs or replaces the file and restarts TAB. Loading the readable records separately, and reloading without a restart, remain future features.

Rejecting unknown keys and malformed tags

JsonAdaptedStudent and JsonSerializableStudentBook use Jackson's @JsonAnySetter callbacks to reject unknown keys while the data is being read, which keeps a hand-edited value from disappearing during a later unrelated save. The student callback names the record and the allowed field names in its error, and permits the removed address key as a compatibility exception; the book also accepts the existing _comment metadata key. JsonStudentBookStorage adds the one-based record number from Jackson's mapping path, so even an unnamed record or two students sharing a name can be located. The shared JSON mapper keeps its existing behavior for preferences, and startup follows the existing loading-error path, leaving rejected data intact.

JsonTagsDeserializer checks the array and string types before adapting tags, so a malformed tags value reports the field and entry position rather than Jackson class names. A missing or null array still means no tags, and tag text continues through the existing model validation. Mapping errors retain their source location and student record number, and do not rewrite the file.

Recovering from bad preferences

JsonUtil.readJsonFile rejects a whole-file null with a DataLoadingException, so both preference and student data loading use their existing error handling instead of crashing, and invalid student data is preserved for repair. JsonUserPrefsStorage likewise rejects an explicit null for guiSettings, while a missing setting retains the UserPrefs defaults. MainApp.initPrefs answers invalid preferences by restoring and saving the defaults before the model is constructed; student data is stored separately and a preference recovery does not touch it.

A recoverable preference write in MainApp.initPrefs or MainApp.stop logs one WARNING naming the preferences path and the I/O reason, without a stack trace. Startup keeps the loaded or default preferences for the session, and shutdown explains that window preferences were not saved. A permission error that carries no reason is described as permission denied.

Confirming a clear

The following state/activity diagram shows the pending-clear confirmation flow:

ClearCommand.execute returns a prompt containing the whole-book count, including students hidden by the current filter. It does not mutate the model. An empty book instead returns a no-op message without a prompt. LogicManager.requestClearConfirmation keeps a non-empty book's request in pendingClearCommand, an Optional<ClearCommand> whose Optional.empty() means nothing is pending, and returns before the usual storage write. While a request is pending, the next input is read as a reply to the concise [y/N] prompt. StringUtil.stripFormatCharacters runs first, sharing the command parser's treatment of copied invisible marks while preserving shaping joiners. Only surrounding Unicode whitespace is then trimmed — internal spaces and visible characters stay, so extra words cannot become a confirmation — and replies ignore case. Trimming scans from both ends with StringUtil.isWhitespace, keeping the command parser's Unicode whitespace rules, and takes linear time at worst, since an internal whitespace run is never searched for a trailing match.

An empty reply, n or no drops the request without executing or saving anything. Only y and yes exactly invoke ClearCommand.executeConfirmed and save the empty book; a word merely starting with either letter, such as yellow or nope, is invalid. Any other input raises a ParseException that repeats the prompt with its feedback and keeps the request pending, and is never executed as another command. Should the reply handler find no request at all — the presence guard means it should not — it raises a CommandException asking the User to enter clear rather than letting an unchecked exception escape. The pending request is cleared before saving, so a storage error cannot leave a stale confirmation active, and it lives only in memory, so restarting TAB cannot confirm a previous request. The prompt and the replies both travel through the existing result area and command field, with no mouse or dialog. MainWindow supplies Logic.isAwaitingConfirmation to CommandBox, which submits an empty Enter only during confirmation; otherwise an empty Enter keeps its existing no-op behavior. Each Logic implementation must supply this state explicitly so a default cannot silently suppress cancellation.

Non-Functional Requirements

  1. Operating environment: Should work on any mainstream OS with Java 25 (64-bit) installed, without requiring platform-specific installation or OS-dependent libraries. The JAR carries JavaFX 17.0.7, whose macOS natives are x86_64, so an Apple Silicon Mac needs either the Azul 25.0.3 JDK+FX distribution the course installs, which supplies JavaFX itself, or an x64 JDK under Rosetta, as the Quick start explains. This satisfies Constraint-Platform-Independent and Constraint-Java-Version.
  2. Portability: Should be packaged as a single executable JAR file of at most 100 MB that runs directly without requiring an installer or system administrator privileges. This satisfies Constraint-Portable, Constraint-Single-File, and Constraint-File-Size.
  3. Single-user operation: Should be designed for a single user operating locally at any given time, without requiring or supporting concurrent multi-user write access to the data file. This satisfies Constraint-Single-User.
  4. CLI-first accessibility: All student management operations must be executable entirely via keyboard commands without requiring a mouse, trackpad, or other pointing device. This satisfies Constraint-Typing-Preferred.
  5. Typing efficiency: A user with above-average typing speed for regular English text should be able to accomplish regular student management tasks faster using CLI commands than using a traditional mouse-driven graphical user interface. This satisfies Constraint-Typing-Preferred.
  6. Capacity: Should comfortably store and manage up to 1,000 student records (sufficient for multiple semesters of active and archived tutorial and lab slots) without noticeable degradation in performance.
  7. Responsiveness: Should execute typical commands (such as adding, editing, deleting, tagging, listing, and filtering across up to 1,000 student records) and update the GUI within 100 milliseconds on standard modern desktop hardware.
  8. Startup time: Should launch and display the GUI, ready for user command input, within 2 seconds on standard modern desktop hardware with an existing data file containing up to 1,000 student records.
  9. Screen resolution and scaling: The GUI should render cleanly without visual clipping or overlapping components at screen resolutions of 1920×1080 and higher with display scaling at 100% and 125%, and remain functional and usable down to 1280×720 with display scaling up to 150%. This satisfies Constraint-Screen-Resolution.
  10. Data locality and offline operation: TAB must store all student data only in local files, must not transmit student data to any network service, and must support all student management operations without a network connection.

Glossary

Names do have a predetermined goodness. If they are straightforward, simple, and do not conflict, then they are called “good names.”

-Xunzi

  • Active list: The student records used for current teaching work, excluding records moved to the proposed archive.
  • Address book: A legacy term found in the upstream AddressBook-Level3 project and retained here only when referring to that project's history. TAB calls its collection of student records the student book.
  • Archive: In the proposed archiving feature, the collection of past student records retained by TAB but excluded from the active list.
  • ASCII space: The ordinary space character (U+0020). This term means that exact character rather than every whitespace character.
  • Class: In the product domain, a tutorial or lab group taught by the User. This is distinct from a Java class.
  • Class tag: A tag used to identify a class.
  • CLI (Command-Line Interface): The keyboard-driven interface through which the User enters commands into TAB.
  • Command option: A separate, hyphen-prefixed token, such as -p or --phone, that identifies the value following it. The add and edit commands use options.
  • Command prefix: A marker attached to the beginning of a field value, such as p/. AB3 marked its fields with prefixes, where TAB uses options.
  • Course: An academic subject (e.g., CS2103T) taught by the User.
  • Data file: The local, human-editable JSON file (tab.json) used by TAB to store student records, distinct from preferences.json.
  • Filtered list: The subset of student records currently visible in the GUI as a result of a filter or search command (such as find or list). Commands taking an Index target records relative to this list.
  • Follow-up: An action or response that the User still owes to a student, tracked in TAB as a pending status on a student record.
  • Identity field: A field used by TAB to identify whether two records refer to the same student. The NUS Student ID is TAB's sole identity field. Name, phone number, and email are searchable details rather than identity keys.
  • Index: The 1-based positive integer identifying a student according to their current display position in the active/filtered list shown in the GUI, rather than a permanent database identifier or 0-based code index.
  • Mainstream OS: Windows, Linux and macOS.
  • NFC (Normalization Form C): The Unicode normalization form TAB uses to store canonically equivalent character sequences consistently.
  • Normalized field value: The standard stored form produced by StringUtil.normalizeFieldValue, allowing input that looks the same to be stored and compared consistently.
  • NUS Student ID: A unique digital identifier for every student at the National University of Singapore. TAB accepts between 1 and 32 ASCII letters and digits, such as A01234567X or E0123456. Lowercase letters are accepted and stored in uppercase.
  • Option: See Command option.
  • Person: A legacy term found in the upstream AddressBook-Level3 project. TAB's model uses Student for a student record.
  • Prefix: See Command prefix.
  • Roster: A list of students belonging to a course, tutorial group, or lab group, particularly one prepared for import into TAB.
  • Semester close-out (proposed): The end-of-semester workflow (UC08) where active student records are archived and the active list is reset in preparation for a new academic term, optionally retaining records with pending follow-ups.
  • Student book: The collection of student records managed by TAB.
  • Student record: The information TAB stores about one student, such as their name, NUS Student ID, phone number, email address, and tags.
  • TAB: Teaching Assistant's Book; the desktop student-management application described in this guide.
  • Tag: A user-defined label attached to a student record for grouping or filtering students.
  • Tag alias: A user-defined shorthand for a longer tag (such as a shortcut for a tutorial group tag), distinct from a command or shell alias.
  • User: The teaching assistant operating TAB.
  • Whitespace: The Unicode characters with the White_Space property, as matched by Java's (?U)\s: U+0009 to U+000D, U+0020, U+0085, U+00A0, U+1680, U+2000 to U+200A, U+2028 to U+2029, U+202F, U+205F and U+3000. This set excludes the zero-width space (U+200B), byte order mark (U+FEFF), zero-width non-joiner (U+200C) and zero-width joiner (U+200D). It governs CommandTokenizer, normalized field values, and top-level command parsing, where StudentBookParser uses StringUtil.isWhitespace to separate the command word from its arguments.

Appendix: Instructions for manual testing

Given below are instructions to test TAB manually.

Note: These instructions only provide a starting point for testers to work on; testers are expected to do more exploratory testing.

Launch and shutdown

  1. Initial launch and where TAB keeps its files

    1. Test case: Copy the JAR into an empty folder, double-click it, add a recognizable student and exit. Then launch the same JAR by its absolute path from a terminal in a different folder.
      Expected: The GUI first opens with sample records, the window size possibly not optimal. The folder beside the JAR then holds data/tab.json, preferences.json and tab.log.0, the student is present, the status bar shows the absolute path to that same file, and nothing is written in the terminal's own folder.

  2. Reading a long data path

    1. Test case: Launch from a folder with a long absolute path and narrow the window until the status bar path no longer fits, then widen it.
      Expected: The path is shortened in the middle, keeping tab.json visible, with the whole path on hover; the tooltip goes once it fits.

  3. Launching from a read-only folder

    1. Prerequisites: Copy the JAR into a folder the account can read but not write, with chmod 555 FOLDER.
    2. Test case: Run java -jar tab.jar there, then add Read Only Test -p 91234567, then exit.
      Expected: The GUI opens with sample records. The terminal warns that it cannot write tab.log and names preferences.json, each without a stack trace or SEVERE label. The add reports a save error and TAB stays open with the record absent, the failed change being rolled back.

  4. Full-page help pager

    1. Test case: Enter help, press Space, b, j, k, g and G, then q.
      Expected: Help replaces the list, sidebar, command box and result area, opening no window or browser, and the notice reads Help mode: press q or Esc to return to commands.. Each key moves as documented, G reaches the last hint with (END) in the footer, and paging past either end stays there. At minimum window size all text stays reachable without scrollbars.
    2. Test case: Read the first screenful, quit, and type add NAME -p PHONE.
      Expected: The margin headings stand out from the body, and in both places add is bold in the accent colour, -p carries the option colour and NAME/PHONE the value colour. In help the brackets around an optional field and the prose lines carry no colour of their own.
    3. Test case: Type find -n Alex without submitting it, press F1, then q. Then enter help oops.
      Expected: The unfinished command returns unselected with the caret at the end and no q inserted, so typing Tan leaves find -n Alex Tan. The second quotes the offending input and opens no page.

  5. Keyboard navigation through students, tags and replies

    1. Prerequisites: Add enough students with distinct tags that both the student list and the tag list overflow.
    2. Test case: Submit list, type find -n Navigation without submitting, then press Tab repeatedly and Shift+Tab back, trying Down, Page Down, End and Home in each list.
      Expected: The cycle is command box → student list → tag list → reply → command box and reverses, each list taking an accent outline when focused. Arrows move by one and page keys by a screenful, End and Home reach either end, and repeating past an end stays there. The draft is unchanged and there is no focus trap.

  6. Saving window preferences

    1. Test case: Resize and move the window, close it, and relaunch.
      Expected: The size and position return when they fit the display.
    2. Test case: With TAB closed, set windowWidth and windowHeight to 1.0E9 and windowCoordinates to {"x":99999,"y":99999}; on a later run replace the file with {"guiSettings": null}.
      Expected: The oversized bounds are corrected so the title bar, command box and status bar stay reachable, and the correction persists. The null settings open with defaults, report GUI settings must not be null., and rewrite a valid file. Student data is untouched either way.

  7. Narrow student cards

    1. Test case: Add add Narrow Card -p "+65 9123 4567" -e a.very.long.address.indeed@u.nus.edu --id AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA, resize to the minimum width, then widen slowly.
      Expected: The ID and email shorten as needed, the phone stays readable, and the email stays inside the card's details area. Worth checking on Windows too, since font widths differ.

Rejecting unexpected command arguments

  1. Commands that take no parameters

    1. Prerequisites: Add a student, run find -n no-such-student to hide them, and keep a copy of data/tab.json.
    2. Test cases: clear oops, list oops, help oops and exit oops.
      Expected: Each reports that it takes no arguments and quotes oops. The list stays filtered, no help opens, TAB stays open and the file matches the copy.
    3. Test cases: clear "" and clear "unfinished.
      Expected: Each reports the unexpected input, including for an empty quoted argument, with nothing changed.
    4. Test case: list and help with only trailing spaces or tabs.
      Expected: Both run normally, trailing whitespace alone not counting as an argument.

Regional settings

  1. Consistent English output

    1. Test case: Launch with java -Duser.language=tr -Duser.country=TR -jar tab.jar and type add Priya -p 91234567 --follow-up.
      Expected: Both options are mauve and the command runs as usual, a locale that lower-cases I differently not disturbing the command words.
    2. Test case: Relaunch under ar / EG, then run list, find -n Priya and clear, cancelling with n.
      Expected: Replies and summary counts use the digits 0–9 rather than the locale's own, and cancelling changes no data.

Typing or mistyping a command word

  1. A correctly spelled command word in capitals

    1. Test cases: List, Help, then ADD McDonald Tan -p 91234567, then LIST oops.
      Expected: Each named command runs, no reply calling the word unknown, and the student is added with the capitals as typed on the card and in the file, the fold reaching the command word alone. The last reads list takes no arguments. Unexpected input: "oops"., naming the command rather than the capitals typed.

  2. A command word one slip away from a real one

    1. Prerequisites: At least one student listed, and a copy of data/tab.json.
    2. Test cases: delte 1, Delte 1, lsit, ls, felete 1, del 3 and cle.
      Expected: Each quotes the word as typed and suggests the command meant — delete, list, delete, clear and so on. Two letters out is still near enough, a wrong first letter does not prevent a suggestion, and a word stopped partway still matches. None runs, the file matching the copy, and the text stays in the box with the line red so the slip can be corrected rather than retyped.
    3. Test case: e.
      Expected: Both edit and exit are named, in that order every time.

  3. A command word resembling nothing TAB knows

    1. Test cases: qwerty, dlt 1 and 日本語, then paste a line of at least 80 characters with no spaces.
      Expected: Each quotes the word and points to help with no suggestion. dlt is two letters from edit but opens with a letter that command does not, so TAB offers nothing rather than guessing. The long paste is quoted to its opening 60 characters followed by an ellipsis, rather than running off the result display.

Follow-up status

  1. Adding students with and without follow-up

    1. Prerequisites: Launch from an empty folder, then clear and reply yes.
    2. Test case: add Alice Tan -p 91234567, then add Bob Lim -p 92345678 --follow-up.
      Expected: Neither Alice's card nor her reply shows Needs follow-up, and her saved record has no flag key. Bob's card and reply both show it and his record holds "flag": true.

  2. Setting and clearing follow-up while editing

    1. Test case: Run edit 1 --follow-up twice, then edit 1 -f, then edit 1 -p 81112222.
      Expected: Alice shows Needs follow-up throughout, repeating either spelling keeping it set, and the phone change leaves it in place.
    2. Test case: Run edit 1 -nf, then edit 1 --no-follow-up, then restart TAB.
      Expected: The label goes with no blank row left behind, repeating either spelling keeps it cleared, and the state survives the restart.

  3. Rejecting invalid or repeated follow-up markers

    1. Test cases: edit 1 --follow-up -f, then edit 1 --follow-up true, then edit 1 --follow-up --no-follow-up.
      Expected: None changes Alice. The first reads Options given more than once: --follow-up. Give each listed option only once.; the second reports that true belongs to no option; the third says the two follow-up options cannot be used together.

  4. Persisting and loading follow-up status

    1. Test case: With TAB closed, replace the file with records using "flag": true, "flag": false, "flag": null and no flag key, then relaunch.
      Expected: Only the first shows Needs follow-up; the rest load as unflagged, including the legacy record with no key.
    2. Test case: With TAB closed, change one record to "flag": 2 and relaunch.
      Expected: The error identifies that record and its invalid flag value, the main window does not open, and the file is left unchanged.

Adding and removing a tag

  1. Preserving the student's other details and persisting the change

    1. Prerequisites: Add add Tag Test -p 91234567 -e tag@example.com --id A01234567X -t T1 --follow-up as one line, then find -n "Tag Test".
    2. Test case: tag 1 --add "Lab 3", then tag 1 --remove " LAB 3 ".
      Expected: The replies start Added tag [Lab 3]: and Removed tag [Lab 3]:. Only that tag comes and goes, T1, the contact details and the follow-up status staying put, the search staying active, and a restart keeping the result. Removal matches whatever case and spacing it is typed in.

  2. Addressing a student by stable ID

    1. Prerequisites: Add add ID Tag Test -p 92345678 --id E7654321 -t T1 and add Numeric Tag Test -p 93456789 --id 1234, then run find -n NoMatchingStudent so both are hidden.
    2. Test case: tag e7654321 --add="Lab 3", then tag -i 1234 -a T2, then tag 1 --id E7654321 -a T2.
      Expected: The first two reach the right student although neither is displayed, preserving the search. A bare tag 1234 -a T2 stays an index request. The third asks for one target and changes nothing.

  3. Reporting duplicate and absent tags

    1. Prerequisites: Return to Tag Test with find -n "Tag Test".
    2. Test case: tag 1 -a T1, then tag 1 -r "Lab 3" once it is gone.
      Expected: This student already has tag [T1]. No changes made. and This student does not have tag [Lab 3]. No changes made., with nothing written either time.
    3. Test case: tag 1 -a "Needs follow-up", then tag 1 -r "Needs follow-up" on this flagged student.
      Expected: Adding is refused, naming --follow-up as the way to mark the student. Removing adds a second line, This student is flagged for follow-up, which is not a tag. To clear the flag, use edit 1 --no-follow-up., the label staying until that edit runs.

  4. Rejecting invalid input without mutation

    1. Test cases: tag 0 -a T2, tag 1 -a "", tag 1 -a, tag 1 -a T2 -r T1, tag 1 -t T2 and tag 1 lab4.
      Expected: Each gives the matching index, invalid-tag, missing-value or conflicting-action error, leaving the student, the list and the file as they were. Wherever the action is left unclear the reply also carries the -a/--add and -r/--remove guidance, naming the unknown -t option and the unexpected value lab4.

  5. Removing a tag that supplies the search match

    1. Test case: tag 1 -a "Lab 3", find -t "Lab 3", then tag 1 -r "Lab 3".
      Expected: The student leaves the filtered list, and list shows them again without that tag.

  6. Reading repeated spellings from a hand-edited file

    1. Test case: With TAB closed set Tag Test's tags to ["Lab 3", " lab 3 ", "T1"], keep "flag": true, restart, and run find -n "Tag Test" then tag 1 -r "LAB 3".
      Expected: The variants load as the single tag Lab 3, which is removed, leaving T1, the flag and every other field after a restart.
